# 서빙 구조 분석 — 데이터 전달 경로와 모델 구동 위치

> 작성 2026-09-14 · 요청: 정선우 님 ("백엔드·DB를 따로 만들어 API로 로드하는 게 나은지" / "AI 모델은 어디서 구동하는 게 좋은지")
> 상태: **분석안**. [`docs/backend-plan.md`](backend-plan.md)가 그린 전체 스택에 대해 **실측값 기준으로 범위를 좁힌 검토**다.
> 채택 여부는 팀 결정 후 [`docs/decisions.md`](decisions.md)에 기록한다.

## 0. 결론 먼저

1. **읽기 경로를 API로 바꾸지 않는다.** 현재 정적 + CDN이 74~205ms인데, 무료 티어 API·DB로는 이길 수 없는 숫자다.
2. **지금 구조의 실제 문제는 성능이 아니라 저장소 비대화다.** payload를 git에 커밋하고 있어 재빌드 1회당 `.git`이 약 30MB 늘어난다.
3. 그래서 **1단계는 백엔드가 아니라 payload를 git 밖으로 빼는 것**이다(§3 방안 B, 약 0.5일).
4. **백엔드·DB는 쓰기 기능(공유 저장, 즉석 추정, 주간 자동 갱신)을 실제로 넣을 때만** 붙인다. 그때도 읽기 경로는 정적으로 남긴다.
5. **horizon 엔진은 서빙 대상이 아니다.** 입력이 변하지 않으므로 배치 전용이며, 무거운 의존성을 가격 모델 함수와 절대 같이 두지 않는다.
6. **가격 모델 추론은 당분간 온라인으로 돌릴 필요가 없다.** 전량 미리 계산돼 있다. 즉석 추정을 넣기로 하면 먼저 모델 아티팩트 크기를 실측해 브라우저 실행 가능 여부부터 가른다.

## 1. 현재 읽기 경로 실측 (2026-09-14)

측정 대상: production `https://imnjang-pi.vercel.app`, 고정 preview `https://imnjang-preview.vercel.app`. 두 배포의 `index.json`은 동일했다(9,160건, `as_of 2026-08-16`, 231,274 bytes).

| 항목 | 원본 | 전송(brotli) | 지연 |
|---|---:|---:|---:|
| `index.json` (전 단지 인덱스) | 1.37 MB | **231 KB** | 205 ms |
| 단지 상세 1건 (중앙값) | 4.9 KB | 약 2 KB | 74 ms |
| 단지 상세 전체 | 56.2 MB (9,160 파일) | — | — |

상세 파일 크기 분포: 최소 1.0KB · 중앙값 4.9KB · p95 12.1KB · 최대 35.7KB.

응답 헤더: `Cache-Control: public, max-age=3600`, `Content-Encoding: br`, `X-Vercel-Cache: HIT`, 엣지 리전 `icn1`(서울).

### 1.1 무결성 확인

| 검사 | 결과 |
|---|---|
| 라이브 `index.json` vs 로컬 파일 | **완전 일치** |
| 인덱스 ID ↔ 상세 JSON 파일 | **1:1 일치** (누락 0, 고아 0) |
| 좌표 결측 | 0건 |
| 라이브 무작위 표본 40건 | 40/40 HTTP 200 |

### 1.2 API 전환이 느려지는 이유

- 검색이 클라이언트 전량 인덱스 기반(`front/lib/data.ts:31`)이라, API로 옮기면 입력마다 왕복이 생긴다. 231KB 한 번이 그보다 낫다.
- 무료 티어의 콜드스타트가 정적 엣지 응답보다 한 자릿수 이상 느리다.
  - Vercel Python 함수: lightgbm·pandas import 포함 시 초 단위
  - Render 무료: 15분 유휴 후 기동에 약 1분
  - Supabase 무료: **1주 미사용 시 프로젝트 자동 일시정지** — 심사 당일 첫 요청이 실패하는 시나리오

## 2. 지금 구조의 실제 문제 — 저장소 비대화

`front/public` 아래 추적 파일이 9,162개(상세 9,160 + `index.json` + `regulation.json`)다. payload를 재빌드하면 거의 전 파일의 내용이 바뀐다.

| 지표 | 값 |
|---|---|
| `.git` pack 크기 | **69.9 MB** |
| payload 재빌드 커밋 횟수 | 2회 (`2d3cb8b`, `c89a2a5`) |
| 재빌드 1회 변경 파일 수 | `9162 files changed` (`2d3cb8b`) |
| 재빌드 1회당 누적 증가 | 약 30 MB (압축 후) |

주간 갱신을 켜면 **연 1.5GB**가 쌓인다. git 히스토리는 되돌릴 수 없고, GitHub는 저장소 1GB부터 경고한다.

즉 백엔드 도입의 진짜 동기는 "읽기가 느려서"가 아니라 **"데이터를 git에 넣고 있어서"** 이며, 이 문제는 DB 없이도 해결된다.

## 3. 선택지 비교

| 방안 | 읽기 지연 | 저장소 증가 | 새 장애 지점 | 작업량 |
|---|---|---|---|---|
| **A. 현행 유지** | 74 ms (엣지) | 주 30 MB ↑ | 없음 | 0 |
| **B. 정적 + 오브젝트 스토리지** — payload를 Supabase Storage / Vercel Blob으로 옮기고 git에서 제거 | 74~150 ms | **0** | 스토리지 1개 | 0.5일 |
| **C. 정적 읽기 + API 쓰기** — 공유·즉석추정만 API, DB는 쓰기 위주 | 74 ms | 0 | API·DB (읽기와 무관) | 2~3일 |
| **D. 전면 API 전환** | 200 ms ~ 수 초(콜드) | 0 | API·DB가 **전 화면 단일 장애점** | 5일+ |

[`backend-plan.md`](backend-plan.md)의 P0~P5는 사실상 D에 가까운 전체 스택을 그려놓았으나, 같은 문서 §0-2도 "지금 화면 기능에는 백엔드가 꼭 필요하지 않다"는 결론을 냈다. 이 분석은 그 결론을 실측으로 뒷받침하면서, **B 단계를 D 이전에 끼워 넣을 것**을 제안한다.

### 3.1 권장: B → (필요 시) C

**B를 먼저.** 백엔드 없이 저장소 문제만 제거한다. `front/public/data`를 gitignore로 돌리고, `36.build_payload.py` 산출물을 오브젝트 스토리지에 업로드하고, 프론트가 그 URL을 읽는다. 읽기 성능·가용성은 그대로고 git 증가가 0이 된다.

**C는 쓰기 기능을 넣기로 결정했을 때.** DB가 아니면 불가능한 것은 다음뿐이다.

| 기능 | 현재 | DB 필요 이유 |
|---|---|---|
| 비교 목록 저장·링크 공유 | 브라우저 localStorage | 서버 측 쓰기 저장소 |
| 사용자 입력 조건 즉석 추정 | 가격 셀 40,848개 전량 미리 계산 | **그리드 밖 조건**을 받을 때만 |
| 주간 실거래 갱신 자동 적재 | 수동 | 배치 스케줄러 + 적재 대상 |

이때도 **읽기 경로는 정적으로 남긴다.** API가 죽어도 검색·비교·지도는 계속 동작해야 한다.

### 3.2 DB 규모는 제약이 아니다

`backend-plan.md` §3.1 기준 적재 대상 40~60MB (최대 테이블은 `comparable` 121,346행 21.8MB). Supabase 무료 500MB 안에 여유가 크다. 원천 거래 원장(매매 37MB / 전월세 189MB)을 넣지 않는 판단은 유지한다.

## 4. 모델 구동 위치

이 프로젝트의 "AI 모델"은 두 개이고 **정답이 서로 반대**다. 런타임 생성형 AI는 없으며, 이는 환각 방지를 위한 의도된 설계다(`docs/architecture.md:17`, `docs/implementation-plan.md:20`).

| 모델 | 무게 | 실시간 필요성 |
|---|---|---|
| **horizon 엔진** (일조·조망) | 서울 전역 **706초(11.8분)**, 48,211동, 관측점당 8.9ms. geopandas·shapely·pyproj·pvlib 필요 | **없음** |
| **가격 모델** (LightGBM) | 300 rounds, `num_leaves=31`, feature 21개 + 법정동 FE. 학습 2024-09~2026-02 | 조건부 |

### 4.1 horizon 엔진 — 서빙 대상이 아니다

입력이 건물 폴리곤과 태양 위치뿐이고 둘 다 변하지 않는다(태양은 결정론적). 사용자 입력으로 바뀌는 값이 하나도 없으므로 **요청 단위로 돌릴 이유가 원천적으로 없다.**

또한 서빙하려면 geopandas + shapely + pyproj + pvlib를 함수 번들에 넣어야 하는데, 이것이 Vercel Python 500MB 한도를 실제로 위협하는 유일한 덩어리다. **가격 모델과 같은 함수에 넣지 않는다.**

→ **GitHub Actions 무료 러너에서 배치.** 11.8분은 작업당 6시간 한도에 여유가 크다. OSM 건물 데이터 갱신 시에만 실행(분기 1회 수준).

### 4.2 가격 모델 — 학습

월 1회 이하로 충분하다. 300 rounds × 31 leaves는 무료 2코어 러너에서 분 단위로 끝나고, 매매 24.7만 행은 메모리 제약이 없다.

→ **GitHub Actions.** 단 `backend-plan.md` §7대로 **주간 갱신에 재학습을 묶지 않는다.** 주간은 거래 수집 + 셀 재계산(`32`)만, 재학습은 월 1회 수동 트리거.

### 4.3 가격 모델 — 추론

**지금은 온라인 추론이 필요 없다.** 가격 셀 40,848개와 추정 6,028행이 전량 미리 계산돼 payload에 들어 있고, 라우팅이 실거래를 우선하므로 모델 값이 실제로 쓰이는 셀은 전체의 13%다.

| source | 셀 수 |
|---|---:|
| `CELL_LAST` (해당 셀 실거래) | 27,549 |
| `AREA_LAST` (같은 면적 다른 층대) | 9,631 |
| **`MODEL` (모델 추정)** | **6,028** |
| `COMPLEX_MEAN` (단지 평균) | 3,668 |
| `EXCLUDED` (임대 전용) | 109 |

온라인 추론은 "사용자가 그리드에 없는 면적·층 조건을 직접 입력"하는 기능을 넣을 때만 필요하다. 그 기능을 전제하면:

| 방안 | 지연 | 비용 | 문제 |
|---|---|---|---|
| **A. 안 함 (현행 배치)** | 0 | 0 | 즉석 조건 불가 |
| **B. 브라우저에서 실행** — 트리 앙상블을 JS로 평가 | ~1 ms | 0 | 아티팩트 다운로드. 동등성 검증이 까다로움 |
| **C. Vercel Python Function** | 콜드 초 단위 / 웜 수십 ms | 무료 한도 내 | 콜드스타트, Hobby 비상업 조항 |
| **D. Cloud Run** | 콜드 1~2초 | 무료 사용량 내 | 결제 계정 필요, 운영 분리 |

**B가 유력하다.** 300트리 × 31리프는 약 9,300개 리프의 순수 트리 앙상블이라 JS 평가 구현이 작고, 서버·DB·콜드스타트가 전부 사라지며, §3의 "정적 읽기 경로 유지" 원칙과 일관된다.

**다만 아직 측정되지 않았다.** 현재 모델은 파일로 저장되지 않는다(`backend-plan.md` §4.1) — `33.train_coldstart.py`가 학습 직후 같은 프로세스에서 추정하고 끝난다. 아티팩트 크기, 법정동 FE 더미를 포함한 feature 벡터 폭, gzip 후 전송량은 저장해봐야 안다. **약 300KB면 B, 수 MB면 C**로 갈린다.

### 4.4 어느 방안이든 필수인 것

- **동등성 게이트**: API든 브라우저든, 같은 입력에 대해 배치 산출물 `33.1` 6,028행과 허용 오차 1e-6 이내로 일치해야 배포한다.
- **feature 생성 재구현 금지**: `_features.py`, `_jeonse.py`, `_price_router.py`를 그대로 import한다. 재구현하면 화면마다 가격이 갈라진다.
- **진실 원천 단일화**: 정적 payload와 DB 적재는 같은 산출물 파일에서 만든다.

## 5. 권장 순서

| 순서 | 내용 | 선행 조건 | 예상 |
|---|---|---|---|
| 1 | horizon을 GitHub Actions 배치로 고정. 서빙 후보에서 제외하고 의존성을 가격 모델과 격리 | — | 0.5일 |
| 2 | 가격 학습을 GitHub Actions 월 1회 수동 트리거로 분리 | — | 0.5일 |
| 3 | **방안 B** — payload를 git 밖 오브젝트 스토리지로. 읽기 경로는 그대로 | — | 0.5일 |
| 4 | `33`에 모델 아티팩트 저장 추가 후 **크기 실측** | — | 1일 |
| 5 | 즉석 추정 요구사항 확정 시 4의 실측값으로 B/C 결정, 동등성 게이트와 함께 구현 | 4 | 1~2일 |

가격 추론은 3~4단계까지 **현행 배치(A)를 유지**한다. 요구사항이 확정되기 전에 서빙 인프라를 만들 이유가 없다.

## 6. 일정 관점

작성 시점은 D6(09-14)이고 제출은 D11(09-19~20)이다. [`project-charter.md`](project-charter.md) §6은 D8에 "Vercel + Supabase"를 두었으나, **제출 전에 읽기 경로를 API로 바꾸는 것은 순수 리스크다** — 얻는 것이 없고 심사 당일 죽을 경로만 하나 늘어난다.

- 제출 전: 1~2단계(배치 분리) + 필요 시 3단계(B)까지
- 제출 후: 4~5단계

## 7. 결정이 필요한 것

1. 방안 B의 저장소 — Supabase Storage / Vercel Blob 중 선택 (DB 도입 여부와 독립)
2. 즉석 추정 기능을 제품에 넣을지. 넣지 않으면 §4.3은 전부 불필요하다
3. 공유 기능(`share`)을 넣을지 — 넣으면 개인정보 없는 익명 목록으로 한정
4. 상용화 가정 시 호스팅 전환 시점 (Vercel Hobby는 비상업·개인 용도만 허용)
