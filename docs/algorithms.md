## 6. 핵심 알고리즘

### 6.1 통합 Horizon Profile 엔진 ★

**이것이 시스템의 심장이다.** 일조·개방도·조망대상·향별 값이 전부 여기서 나온다.

**관측 단위**: `건물(building) × 층대(floor_band)` — 3개 층대
따라서 관측점 수 = 약 40,000동 × 3 = **120,000**

| 층대 | 정의 | 대표 층 |
|---|---|---|
| 저층 | 2층 ~ ⌊N/3⌋ | ⌈N/6⌉ |
| 중층 | ⌊N/3⌋+1 ~ ⌊2N/3⌋ | ⌈N/2⌉ |
| 고층 | ⌊2N/3⌋+1 ~ N | ⌈5N/6⌉ |

(N = 해당 동의 지상 층수. 1층은 별도 처리 — 조경·담장 영향이 커서 모델 밖)

**관측 높이 (AMSL)** = `자기 동 지반고(DEM) + (대표층 − 1) × 2.8m + 1.5m`
**관측 위치** = 동 폴리곤 중심 (외벽 중점이 아님 — §6.2 aspect 정의 참조)

#### 계산 방법 (핵심 최적화)

광선-폴리곤 교차 검사를 하지 않는다. 대신:

```
1. R-tree로 관측점 반경 1km 내 건물 후보 추출        (1회)
   ★ 자기 자신의 building_id를 후보에서 반드시 제외한다   ← v3 수정 ①
2. 후보 건물 외곽선을 거리 비례 adaptive densify → 점 집합  ← v3 수정 ③
     간격 = clip(거리 × tan(2.5°), 0.5m, 5m)
     즉 10m 거리는 0.5m 간격, 500m 거리는 5m 간격
     50m 이내 후보는 edge 중점까지 추가 샘플링
3. 각 점을 관측점 기준 극좌표로 변환 (numpy 벡터화)
     방위각 θ = atan2(dy, dx)
     앙각   φ = arctan((후보건물_상단높이 − 관측높이) / 수평거리)
     ★ 후보건물_상단높이 = 해당 건물 지반고(DEM) + 지상층수 × 2.8m   ← v3 수정 ②
       (관측높이와 동일하게 AMSL. AGL과 섞으면 경사지에서 수십 m 오차)
4. 방위를 5° 간격 72개 bin으로 나누고, bin별 max(φ) 취함
     → horizon profile: 72개 앙각 배열
```

전체가 numpy 배열 연산 한 덩어리이므로 shapely 스칼라 루프 대비 수십 배 빠르다.

**성능을 위한 전제 (D1에 반드시 구현)**
- densify한 외곽점을 건물별로 **사전 캐시**한다. 관측점마다 다시 densify하면 수십 시간으로 무너진다
- R-tree 조회는 **동 중심당 1회**. 3개 층대가 동일한 거리·방위 배열을 재사용한다 (층대는 관측높이만 다르므로 φ만 다시 계산)

#### 이 방법의 알려진 근사 오차 (계획서에 남기고, 앱 §3.4에도 표기)

| 근사 | 영향 | 판단 |
|---|---|---|
| bin 내 최대 앙각으로 bin 전체를 차폐 처리 | 실제 광선 위에 없는 점이 차폐로 잡힐 수 있음 (false positive) | 5° bin에서 수용 |
| 직선 edge의 최대 앙각이 꼭짓점이 아닌 edge 내부에 있을 수 있음 | 과소평가 (false negative) | adaptive densify로 대부분 해소 |
| 오목(concave) 폴리곤 | 같은 bin의 점이 실제 중심 광선을 막지 않을 수 있음 | 아파트 동은 대부분 볼록/판상형 → 수용 |
| 반경 1km cutoff | **일조: 영향 없음.** 서울 동지 남중고도 ≈29°, 1km에서 29° 앙각은 높이 554m 필요 (롯데월드타워급 1개뿐). **조망(10° 기준): 176m 이상 초고층은 누락** | 일조는 정확, 조망은 한계 명시 |
| 층고 2.8m 균일 가정, 옥탑·경사지붕 무시 | 수 m 오차 | 수용, 명시 |

> `1km / 5° / 5m`는 **정확도 보장값이 아니라 설정 가능한 근사 파라미터**다. 코드에서 상수가 아니라 config로 노출하고, 앱 근거 화면에 현재 값을 표시한다.

#### 6.1.1 조망 대상 판정 (한강·공원·산) — 별도 LOS

profile만으로는 "트인 방향에 한강이 있다"까지만 알 수 있고 **"한강이 보인다"는 증명되지 않는다.** 별도 판정을 둔다.

```
1. 관측점 기준 반경 3km 내 한강·주요 공원 폴리곤, DEM 고지대를 대상으로 삼는다
2. 각 대상에 대해 관측점→대상 방위 구간을 구한다
3. 그 방위 구간에서 profile 앙각 < 대상까지의 시선 앙각 인지 확인
   (즉 그 방향의 스카이라인이 대상을 가리지 않는지)
4. 통과하면 river_view = TRUE
```

대상 수가 적으므로(단지당 수 개) 추가 비용은 무시할 수준이다.
UI 문구는 **"북동 방향으로 한강 시야가 열려 있음(추정)"** 으로, 단정하지 않는다.

#### 축소 경로 (추정 시간이 과도할 경우 순서대로 적용)

1. 반경 1km → 500m
2. 방위 bin 5° → 10° (72 → 36)
3. densify 간격 5m → 10m
4. 층대 3 → 2 (저·고)
5. 핵심 5개 구(강남·서초·송파·마포·성동) 우선 완료 후 나머지 백그라운드

### 6.2 향(aspect)의 정의 — 정직하게

**문제**: 실거래에 향 정보가 없고, 건물 폴리곤 중심은 실제 세대 창 위치가 아니다.

**v2의 처리**:
- 향은 **관측된 사실이 아니라 시나리오**로 제시한다
- UI 문구: *"이 동의 남향 세대라면"* (단정하지 않음)
- 계산: 동 폴리곤 중심의 horizon profile을 해당 방위 ±60°로 슬라이스
- 앱 내 §3.4 한계표에 "세대별 실제 창 위치는 알 수 없음"을 명시

이 처리는 정확도를 낮추지만 **거짓말을 하지 않는다.** 향 정보를 확정적으로 주장하는 것보다 낫다.

### 6.3 도로·철도 근접도 (소음 모델 강등)

**v1에서 변경**: 소음 dB 추정 모델을 폐기했다. 캘리브레이션할 실측 라벨이 없는 상태에서 소음 수치를 주장할 근거가 없다.

**v2**: 검증 가능한 **사실만** 표기한다.

| 표기 | 근거 |
|---|---|
| **"간선도로 중심선까지 45m"** | OSM 도로 위계 + 거리 계산. 사실 |
| "지상 철도 중심선까지 220m" | 좌표 계산. 사실 |
| "동과 도로 사이에 다른 동이 있음" | 폴리곤 차폐 판정. 사실 |
| ~~"도로 경계 45m"~~ | **OSM은 centerline이고 차폭 데이터가 없다.** "경계"라고 쓰면 사실 표기가 아니다 |
| ~~"소음 62dB 추정"~~ | **주장하지 않음** |

UI에서는 "조용함 점수" 대신 **"소음원 근접도"** 라는 중립적 이름을 쓴다.

> 실측 데이터(국가소음정보시스템 측정소)를 확보하면 상관 검증 후 dB 추정을 복원한다. 확보 못 하면 복원하지 않는다.

### 6.4 표고 및 접근성

**v1에서 변경**: 카카오 도보경로 API는 **일 1,000건 제한**으로 4,000단지 계산이 불가능하다. 폐기.

**v2**:
- `단지 중심 ↔ 최근접 지하철역` **직선거리** + **표고차**(DEM)
- 도보 시간은 직선거리 × 1.3(우회계수) ÷ 4km/h 로 추정한다
- **UI 문구는 "도보 10분"이 아니라 "추정 도보 10분"이며, 필터 라벨도 "추정 도보시간"으로 쓴다.** 실제 경로를 계산하지 않았으므로 단정하면 거짓 표기가 된다
- **단지 내부 경사는 계산하지 않는다.** Copernicus 30m DEM은 픽셀 하나가 건물 여러 동을 덮어 단지 내부 고저차를 표현할 수 없다
- NGII 5m DEM을 Day 1에 확보하면 단지 진입 경사까지 확장. 못 하면 단지-역 간 표고차만 제공

### 6.5 가격 모델 (v3 — baseline-first)

> 2026-09-12 전면 개정. 실측 근거는 [`product-identity.md`](product-identity.md) §5.

**v2에서 변경 — 모델의 역할을 좁혔다.**

최근 24개월 학습·2026-03~08 out-of-time 평가에서, **평가한 모델들은 같은 단지의 거래가 있는 구간에서 실거래 baseline보다 낮은 MAPE를 보이지 못했다.**

| 구간 | 비중 | 실거래 baseline | 모델 |
|---|---|---|---|
| 동일 셀 직전 거래 있음 | 91.9% | **7.95%** | 18.46% |
| 단지 평균은 있음 | 3.6% | **14.64%** | 23.71% |
| **단지 이력 자체가 없음** | 4.5% | B2 global-mean fallback 64.65% | 탐색 모델 M3 **21.16%** |

따라서 화면은 baseline-first다. 이 평가에서 모델의 상대적 개선이 확인된 구간은 **cold-start 4.5%뿐**이다 (`output/30.3.baseline_breakdown.txt`).

**cold-start 모델**

| 항목 | 내용 |
|---|---|
| 대상 | 최근 24개월 매매 0건인 2,318단지 중 임대 전용 109개를 뺀 **2,206단지** |
| 알고리즘 | LightGBM (OLS·Ridge·RandomForest·XGBoost·CatBoost와 비교 후 채택. 부스팅 3종은 0.26%p 안에 동률이라 학습 속도와 기존 conformal 정합성으로 결정) |
| 학습 기간 | **최근 24개월만.** 지표가 2026년 현재 상태라 5년치를 쓰면 시점 불일치가 생긴다 |
| 전세 활용 | 면적타입 발견(1,025→2,315단지) + 가격 feature. 단지 홀드아웃 12.65%→9.73% (`output/33.2`) |
| 예측구간 | split conformal. calibration을 **시간×단지 이중 분할**로 잡아야 한다 — 단지만 나누면 시점 이동 오차를 담지 못해 coverage가 70.92%로 떨어진다 |
| 성능 | 단지 홀드아웃 MAPE **9.73%** / test coverage **84.42%** (명목 80%). 평가 모집단이 추정 대상과 달라 추정 대상 전체 성능으로 말하지 않는다 |

**물리 feature는 가격 모델에서 뺀다.**

지역 fixed effect를 완전 법정동 키로 고친 뒤 재측정하니, 이 사양·이 평가기간에서 물리 feature의 추가 예측 개선을 확인하지 못했다 (M2 vs M3 MAPE 차이 bootstrap 95% CI **[-0.039234, +0.104810]%p**, 0 포함). 통계적 연관은 남지만(joint Wald p=3.07272e-22) 예측 개선과는 별개다. 일조·조망은 **환경 비교 화면 전용**이다.

**말할 수 있는 것 / 없는 것**

| 말할 수 있다 | 말할 수 없다 |
|---|---|
| "이 단지 이 면적의 최근 거래는 14.2억이다" | "적정시세는 14.2억이다" |
| "이 train M3 사양에서 `river_view`는 다른 조건이 같을 때 가격과 +6.0276% 조건부 연관을 보였다" | "이 집은 조망 때문에 3억 비싸다" |
| "일조의 가격 영향은 확인되지 않았다" | "일조는 가격에 반영되지 않는다" |

**SHAP는 폐기한다.** 상관된 feature의 attribution은 배경 설정에 좌우되고 인과를 뜻하지 않는다.

**호가 데이터 부재 대응**은 v2와 같다. 저평가 판정을 자동으로 하지 않는다.

### 6.6 실거주 적합도 종합 점수 — **폐기**

> 2026-09-12 폐기. 종합 판정은 주관이며 반박 가능하다. 제품은 사용자가 고른 단지를 같은 축에 나란히 놓는 데까지만 한다 (`product-identity.md` §3). 아래는 이력 보존용이다.


물리 지표를 0~100으로 정규화한 뒤 **사용자 조절 가중합**으로 계산한다.

```
종합점수 = Σ (정규화점수_i × 가중치_i)
```

| 프리셋 | 강조 |
|---|---|
| 신혼부부 | 역 접근성, 편의점·음식점 밀도, 공원, 조용함 |
| 아이 있는 집 | **초품아**, 어린이집, 소아과, 공원, 교통량 낮음, 야간상권 낮음 |
| 재택근무 | 일조, 개방감, 조용함, 교통량 낮음, 마트 |
| 시니어 | 평지(표고차), **종합병원 거리**, 일조, 마트 |
| 1인 가구 | 역 접근성, 편의점·음식점 밀도, 야간상권 **무관 또는 선호** |
| 투자 관점 | 거래량, 전세가율, 정비사업, **용적률 낮음(사업성)**, 역 승하차 |

> **이것은 ML이 아니라 가중합 규칙이다.** UI에서 ML 산출물과 규칙 기반 산출물을 시각적으로 구분 표기한다. 전부 AI라고 우기지 않는 것이 신뢰를 만든다.

### 6.7 조건 완화 추천 ★ (v3 신규)

**해결하는 문제**: 필터를 걸었는데 결과가 0개면 사용자는 막힌다. 검색은 되는데 의사결정은 안 되는 상태다.
어떤 조건을 얼마나 풀어야 하는지는 사용자가 조건을 하나씩 바꿔가며 시행착오로 찾아야 하는데, 조건이 4~5개면 조합이 폭발한다.

**동작**: 조건 만족 단지가 0개이거나 3개 미만일 때, **가장 적게 포기하는 조합**을 제시한다.

```
조건 만족: 0개 단지

  ▸ 겨울 일조 5.0h → 4.5h 로만 낮추면        +8개 단지
  ▸ 추정 도보 10분 → 12분 으로만 늘리면      +11개 단지
  ▸ 매매가 10억 → 10.8억 으로만 올리면       +6개 단지
  ▸ 일조 4.5h + 도보 12분 (둘 다 조금씩)     +23개 단지
```

**계산 방법** (새 데이터·새 모델·새 배치 불필요)

```
1. 각 단지가 위반한 조건과 위반 정도를 구한다
     violation_i = (조건값 − 실제값) / 조건 범위     ← 0~1로 정규화
2. 단지별 총 위반량 = Σ violation_i
3. 총 위반량이 작은 순으로 정렬
4. 상위 단지들이 위반한 조건을 집계하여
   "이 조건을 이만큼 풀면 몇 개가 들어온다"를 역산
5. 단일 조건 완화 3개 + 복합 완화 1개를 제시
```

이미 계산된 `complex_metrics`만 사용하므로 **클라이언트 측에서 즉시 계산된다.** 서버 왕복도 없다.

**왜 이 기능이 중요한가**
- 필터를 *검색 도구*에서 *의사결정 도구*로 바꾼다. "없다"가 아니라 "이만큼 양보하면 있다"를 말한다
- 빈 결과 화면이라는 최악의 UX를 제거한다
- 전 단지 사전 계산(§3.2)이 있어야만 가능하다 → **차별점을 한 번 더 강화한다.** 경쟁사는 단지를 하나씩 열어보는 구조라 이 계산 자체가 불가능하다

**구현 순서**: Layer 1(S1 필터)이 D6에 동작한 뒤에만 착수한다. 필터가 없으면 완화할 조건도 없다.

### 6.8 생활 인프라 및 유동 지표 (v3 신규)

전부 **POI 좌표와의 거리·개수 집계**이므로 horizon 엔진 대비 연산 비용이 무시할 수준이다. 그러나 실거주자가 실제로 따지는 항목이고, 필터 조건으로 쓸 수 있어 §3.2 전역 탐색의 가치를 직접 키운다.

#### 6.8.1 교육

| 지표 | 계산 | 비고 |
|---|---|---|
| 초등학교 최단거리 | 직선거리 | **학교 직선 경로 근사**(`elem_safe_route`): 단지→최근접 초등학교 직선이 간선도로와 교차하지 않으면 true. **거리 조건은 구현하지 않았다**(학교가 300m 넘게 먼데 true 인 단지 4,169곳). "초품아"로 표기하지 않는다 |
| 초등학교 통학로 도로 횡단 여부 | 단지→학교 직선 경로가 주간선도로와 교차하는지 | 사실 표기 |
| 중·고등학교 최단거리 | 직선거리 | |
| 어린이집·유치원 500m 내 개수 | 카운트 | |
| 학군 밀도 | 1km 내 학교 수 | |

> 학업 성취도·진학률은 **다루지 않는다.** 무료로 신뢰할 수 있게 얻기 어렵고, 잘못 쓰면 서열화 논란을 부른다.

#### 6.8.2 의료

심평원 병원정보서비스 OpenAPI(무료, 영리 이용 허용 명시)를 사용한다. 종별 구분이 있어 거리만이 아니라 **급수**를 볼 수 있다.

| 지표 | 계산 |
|---|---|
| 상급종합병원 최단거리 | 직선거리 |
| 종합병원 최단거리 | 직선거리 |
| 1km 내 의원 수 | 카운트 (소아과·내과 별도 집계) |
| 응급 대응 | 종합병원 이상 3km 이내 여부 |

#### 6.8.3 생활 편의

| 지표 | 출처 | 계산 |
|---|---|---|
| 대형마트 최단거리 | 대규모점포 표준데이터 | 직선거리 |

#### 6.8.4 새벽배송 — 서울에서는 변별력이 없음 (확인 완료)

| 서비스 | 커버리지 | 서울 내 변별력 |
|---|---|---|
| 마켓컬리 샛별배송 | **서울·인천·경기 전역** | **없음** |
| 쿠팡 로켓프레시 | **수도권·광역시·제주** | **없음** |

서울 전역이 이미 커버되므로 **필터 조건으로 쓰면 의미가 없다.** (모든 단지가 통과한다)

**처리**
- S2 리포트에 **"새벽배송 가능(컬리·쿠팡)" 배지로 표기만** 한다. 사용자가 궁금해하는 항목이므로 답을 준다
- **S1 필터에는 넣지 않는다.** 변별력 0인 조건을 필터에 두면 사용자를 속이는 것이다
- 경기·인천으로 확장하면(§12) 변별력이 생기므로 그때 필터로 승격한다
- 권역 데이터는 공개 API가 없으므로 **"서울 전역 가능"이라는 사실만 하드코딩**한다. 크롤링하지 않는다

#### 6.8.5 야간 상권 밀도 (유흥시설)

소상공인 상가DB 업종 대분류로 주점·유흥업소를 집계한다.

| 지표 | 계산 |
|---|---|
| 300m 내 주점·유흥업소 수 | 카운트 |
| 최근접 유흥 밀집지 거리 | 카운트 밀도 상위 클러스터까지 거리 |

**표기 원칙**: "유흥가 근처라 나쁨" 같은 단정을 하지 않는다. 중립적으로 **"야간 상권 밀도"** 로 표기하고, 사용자 가중치에서 선호/기피를 스스로 정하게 한다. (1인 가구는 선호할 수도 있다)

#### 6.8.6 유동 지표

| 지표 | 출처 | 의미 | 한계 |
|---|---|---|---|
| **지하철 역별 승하차 인원** | 서울교통공사(서울열린데이터광장) | 최근접 역의 활성도. 역세권의 "급"을 나타냄 | 역 단위. 단지별로는 최근접 역 값을 부여 |
| **평일/주말 교통량** | 서울시 지점별 교통량 | 인접 도로의 차량 통행량. 소음·매연·보행 안전의 대용 지표 | **지점 관측이다.** 서울 전역 도로를 덮지 않음 |
| 생활인구 밀도 (주간/야간) | 서울열린데이터광장 250m 격자 | 주변 활동 인구 | 대용량. 우선순위 낮음 |

> **교통량의 한계를 반드시 명시한다.** 지점 관측이므로 관측 지점이 없는 도로는 값이 없다.
> 처리: 최근접 관측 지점의 값을 **같은 도로 위계 내에서만** 부여하고, 300m 이내에 관측 지점이 없으면 **"관측 지점 없음"으로 표기하고 결측 처리**한다. 공간 보간으로 없는 숫자를 만들어내지 않는다.

#### 6.8.7 단지 자체 밀도 (호갱노노에 있는 항목)

이미 §7 `complex` 테이블에 있으나 **S2 리포트에 표시되지 않고 있었다.** 추가한다.

| 지표 | 의미 |
|---|---|
| **건폐율** | 낮을수록 동 간 간격이 넓고 단지 내 공지가 많음 |
| **용적률** | 낮을수록 저밀. 재건축 사업성과도 직결 |
| 세대당 주차대수 | 주차난 예측 |
| 세대당 대지지분 | 재건축 가치 (총 대지면적 / 세대수) |
| 동당 평균 세대수 | 판상형/타워형 성격 추정 |

**건폐율·용적률은 horizon 결과와 교차 해석할 때 특히 유용하다.** "건폐율이 낮은데 일조도 좋다"는 서로를 뒷받침하고, "건폐율은 낮은데 일조가 나쁘다"면 주변 외부 건물 탓임을 알 수 있다. 이 교차 해석을 S3 근거 화면에 넣는다.

전부 넣으면 D2~D3 수집 부담이 늘어난다. 다음 순서로 확보하고, D3가 밀리면(§10.3) 아래에서부터 자른다.
