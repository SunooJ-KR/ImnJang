# 서빙 구조 분석 — 데이터 전달 경로와 모델 구동 위치

> 작성 2026-09-14 · 요청: 정선우 님 ("백엔드·DB를 따로 만들어 API로 로드하는 게 나은지" / "AI 모델은 어디서 구동하는 게 좋은지" / "Railway 유료 구독 중인데 DB를 별도 구축하는 게 효율적인지")
> 상태: **분석안**. [`docs/backend-plan.md`](backend-plan.md)가 그린 전체 스택에 대해 **실측값 기준으로 범위를 좁힌 검토**다.
> 채택 여부는 팀 결정 후 [`docs/decisions.md`](decisions.md)에 기록한다.

## 0. 결론 먼저

1. **읽기 경로를 API로 바꾸지 않는다.** 현재 정적 + CDN이 74~205ms다. 이는 요금제 문제가 아니라 위치 문제이므로 **유료 인프라를 써도 서울 엣지 캐시보다 빨라지지 않는다.**
2. **지금 구조의 실제 문제는 성능이 아니라 저장소 비대화다.** payload를 git에 커밋하고 있어 재빌드 1회당 `.git`이 약 30MB 늘어난다.
3. **Railway 유료 구독이 있으면 DB를 별도 구축하는 편이 낫다.** 단 읽기 경로 교체용이 아니라 **진실 원천(system of record) · 상시 가동 추론 API · 배치 워커** 용도다(§5).
4. **horizon 엔진은 서빙 대상이 아니다.** 입력이 변하지 않으므로 배치 전용이며, 무거운 의존성을 가격 모델 서비스와 절대 같이 두지 않는다.
5. **가격 모델 추론은 지금 온라인으로 돌릴 필요가 없다.** 전량 미리 계산돼 있다. 즉석 추정을 넣기로 하면 **상시 가동 API(방안 C)** 로 간다 — Railway가 콜드스타트를 제거하므로 브라우저 실행(B)의 이점이 사라지고, 동등성 검증은 C가 압도적으로 쉽다.
6. **읽기 경로 정적 유지**와 **동등성 게이트**(§4.4)는 인프라 선택과 무관하게 지킨다.

## 1. 현재 읽기 경로 실측 (2026-09-14)

측정 대상: production `https://imnjang-pi.vercel.app`, 고정 preview `https://imnjang-preview.vercel.app`. 두 배포의 `index.json`은 동일했다(9,160건, `as_of 2026-08-16`, 231,274 bytes).

| 항목 | 원본 | 전송(brotli) | 지연 |
|---|---:|---:|---:|
| `index.json` (전 단지 인덱스) | 1.37 MB | **231 KB** | 205 ms |
| 단지 상세 1건 (중앙값) | 4.9 KB | 약 2 KB | 74 ms |
| 단지 상세 전체 | 56.2 MB (9,160 파일) | — | — |

상세 파일 크기 분포: 최소 1.0KB · 중앙값 4.9KB · p95 12.1KB · 최대 35.7KB.

응답 헤더: `Cache-Control: public, max-age=3600`, `Content-Encoding: br`, `X-Vercel-Cache: HIT`, 엣지 리전 `icn1`(서울).

### 1.1 무결성 확인

| 검사 | 결과 |
|---|---|
| 라이브 `index.json` vs 로컬 파일 | **완전 일치** |
| 인덱스 ID ↔ 상세 JSON 파일 | **1:1 일치** (누락 0, 고아 0) |
| 좌표 결측 | 0건 |
| 라이브 무작위 표본 40건 | 40/40 HTTP 200 |

### 1.2 API 전환이 느려지는 이유 (요금제와 무관)

- 정적 경로는 **서울 엣지에서 캐시 적중**해 컴퓨트 0으로 2KB를 돌려준다. 어떤 API도 여기에 왕복·쿼리·직렬화를 더한 값보다 빨라질 수 없다.
- 검색이 클라이언트 전량 인덱스 기반(`front/lib/data.ts:31`)이라, API로 옮기면 입력마다 왕복이 생긴다. 231KB 한 번이 그보다 낫다.
- 정적 경로에는 **런타임 장애 모드가 없다.** API로 옮기면 컨테이너 재시작·OOM이 전 화면 장애가 된다.

> Railway 리전은 확인이 필요하다(§5.4). 다만 리전이 어디든 위 세 가지는 성립하므로 **권장은 리전에 따라 바뀌지 않는다.**

## 2. 지금 구조의 실제 문제 — 저장소 비대화

`front/public` 아래 추적 파일이 9,162개(상세 9,160 + `index.json` + `regulation.json`)다. payload를 재빌드하면 거의 전 파일의 내용이 바뀐다.

| 지표 | 값 |
|---|---|
| `.git` pack 크기 | **69.9 MB** |
| payload 재빌드 커밋 횟수 | 2회 (`2d3cb8b`, `c89a2a5`) |
| 재빌드 1회 변경 파일 수 | `9162 files changed` (`2d3cb8b`) |
| 재빌드 1회당 누적 증가 | 약 30 MB (압축 후) |

주간 갱신을 켜면 **연 1.5GB**가 쌓인다. git 히스토리는 되돌릴 수 없고, GitHub는 저장소 1GB부터 경고한다.

즉 백엔드 도입의 진짜 동기는 "읽기가 느려서"가 아니라 **"데이터를 git에 넣고 있어서"** 다.

## 3. 선택지 비교

| 방안 | 읽기 지연 | 저장소 증가 | 새 장애 지점 | 작업량 |
|---|---|---|---|---|
| **A. 현행 유지** | 74 ms (엣지) | 주 30 MB ↑ | 없음 | 0 |
| **B. 정적 + 외부 저장소** — payload를 git 밖으로, 읽기는 그대로 | 74~150 ms | **0** | 저장소 1개 | 0.5일 |
| **C. 정적 읽기 + API 쓰기** — 공유·즉석추정만 API | 74 ms | 0 | API·DB (읽기와 무관) | 2~3일 |
| **D. 전면 API 전환** | 100 ms ~ 수 초 | 0 | API·DB가 **전 화면 단일 장애점** | 5일+ |

[`backend-plan.md`](backend-plan.md)의 P0~P5는 사실상 D에 가까운 전체 스택을 그려놓았으나, 같은 문서 §0-2도 "지금 화면 기능에는 백엔드가 꼭 필요하지 않다"는 결론을 냈다. 이 분석은 그 결론을 실측으로 뒷받침하면서 **B를 D 이전 단계로 끼워 넣고, Railway 보유를 전제로 B의 저장소를 DB로 승격**한다(§5).

### 3.1 DB 규모는 제약이 아니다

`backend-plan.md` §3.1 기준 적재 대상 40~60MB (최대 테이블은 `comparable` 121,346행 21.8MB). Railway Postgres에서는 물론이고 무료 티어 기준으로도 여유가 있다. 원천 거래 원장(매매 37MB / 전월세 189MB)을 넣지 않는 판단은 유지한다.

## 4. 모델 구동 위치

이 프로젝트의 "AI 모델"은 두 개이고 **정답이 서로 반대**다. 런타임 생성형 AI는 없으며, 이는 환각 방지를 위한 의도된 설계다(`docs/architecture.md:17`, `docs/implementation-plan.md:20`).

| 모델 | 무게 | 실시간 필요성 |
|---|---|---|
| **horizon 엔진** (일조·조망) | 서울 전역 **706초(11.8분)**, 48,211동, 관측점당 8.9ms. geopandas·shapely·pyproj·pvlib 필요 | **없음** |
| **가격 모델** (LightGBM) | 300 rounds, `num_leaves=31`, feature 21개 + 법정동 FE. 학습 2024-09~2026-02 | 조건부 |

### 4.1 horizon 엔진 — 서빙 대상이 아니다

입력이 건물 폴리곤과 태양 위치뿐이고 둘 다 변하지 않는다(태양은 결정론적). 사용자 입력으로 바뀌는 값이 하나도 없으므로 **요청 단위로 돌릴 이유가 원천적으로 없다.**

또한 geopandas + shapely + pyproj + pvlib는 이미지·번들을 가장 크게 만드는 덩어리다. **가격 모델 서비스와 같은 이미지에 넣지 않는다.** 배치 워커 이미지로 분리한다.

→ 실행 위치: **배치 워커**(Railway cron 또는 GitHub Actions). 11.8분이면 어느 쪽이든 여유가 크다. OSM 건물 데이터 갱신 시에만 실행(분기 1회 수준).

### 4.2 가격 모델 — 학습

월 1회 이하로 충분하다. 300 rounds × 31 leaves는 2코어에서 분 단위로 끝나고, 매매 24.7만 행은 메모리 제약이 없다.

→ **배치 워커에서 월 1회 수동 트리거.** `backend-plan.md` §7대로 **주간 갱신에 재학습을 묶지 않는다.** 주간은 거래 수집 + 셀 재계산(`32`)만.

### 4.3 가격 모델 — 추론

**지금은 온라인 추론이 필요 없다.** 가격 셀 40,848개와 추정 6,028행이 전량 미리 계산돼 payload에 들어 있고, 라우팅이 실거래를 우선하므로 모델 값이 실제로 쓰이는 셀은 전체의 13%다.

| source | 셀 수 |
|---|---:|
| `CELL_LAST` (해당 셀 실거래) | 27,549 |
| `AREA_LAST` (같은 면적 다른 층대) | 9,631 |
| **`MODEL` (모델 추정)** | **6,028** |
| `COMPLEX_MEAN` (단지 평균) | 3,668 |
| `EXCLUDED` (임대 전용) | 109 |

온라인 추론은 "사용자가 그리드에 없는 면적·층 조건을 직접 입력"하는 기능을 넣을 때만 필요하다. 그 기능을 전제하면:

| 방안 | 지연 | 동등성 검증 | 판단 |
|---|---|---|---|
| **A. 안 함 (현행 배치)** | 0 | 불필요 | 요구사항 확정 전 기본값 |
| **B. 브라우저에서 트리 앙상블 평가** | ~1 ms | **어려움** — feature 생성을 JS로 재구현해야 하며 §4.4 위반 | **폐기** |
| **C. 상시 가동 API** (Railway) | 웜 1~5 ms | **쉬움** — `_features.py` 등을 그대로 import | **채택** |
| D. 서버리스 함수 | 콜드 초 단위 | 쉬움 | 콜드스타트 때문에 열위 |

무료 티어 전제에서는 콜드스타트가 없다는 이유로 B가 유력했다. **Railway 상시 가동이 그 이점을 무효화하므로 C가 명확히 낫다.** B는 §4.4가 금지한 feature 재구현을 강요한다는 점에서 구조적으로 열위다.

**선행 작업은 그대로 필요하다.** 현재 모델은 파일로 저장되지 않는다(`backend-plan.md` §4.1) — `33.train_coldstart.py`가 학습 직후 같은 프로세스에서 추정하고 끝난다. 서빙하려면 booster · feature 목록 · 법정동 dense key · conformal 분위수 · 학습 기준월을 아티팩트로 저장해야 한다.

### 4.4 어느 방안이든 필수인 것

- **동등성 게이트**: 같은 입력에 대해 배치 산출물 `33.1` 6,028행과 허용 오차 1e-6 이내로 일치해야 배포한다.
- **feature 생성 재구현 금지**: `_features.py`, `_jeonse.py`, `_price_router.py`를 그대로 import한다. 재구현하면 화면마다 가격이 갈라진다.
- **진실 원천 단일화**: 정적 payload와 DB는 같은 원천에서 만든다(§5.1).

## 5. Railway 전제 구성

팀이 Railway 유료 구독을 보유하고 있다. 이는 무료 티어 전제에서 백엔드를 미루게 했던 근거 중 상당수를 제거한다.

| 무료 티어 전제의 제약 | Railway 유료에서 |
|---|---|
| Supabase 1주 미사용 시 자동 일시정지 → 심사 당일 DB 사망 | **해소.** 상시 가동 |
| 서버리스 콜드스타트 (Python 함수 초 단위 / Render 약 1분) | **해소.** lightgbm을 메모리에 상주 |
| Vercel Hobby 비상업·개인 용도 조항 | **완화.** API를 Railway에 두면 상용 전환 시에도 문제없음 |
| GitHub Actions 작업당 6시간 제한 | **해소.** 워커에 시간 제약 없음 |

**그러나 §1.2의 읽기 경로 결론은 바뀌지 않는다.** 상시 가동이어도 왕복·쿼리·직렬화가 서울 엣지 캐시 적중보다 빠를 수 없고, 단일 컨테이너는 새로운 전면 장애 모드다.

### 5.1 권장 구성

```text
[배치 워커 · Railway]   수집 → 마스터 → 지표 → 가격(30~34)
                              ↓
[Railway Postgres]      진실 원천 (스냅샷 단위 교체, as_of 컬럼)
                              ↓
                        payload 빌드(36) → 정적 호스팅 업로드
                              ↓
[브라우저]              정적 JSON 읽기 (기존 그대로, 엣지 캐시)
                        + /api/* (쓰기·즉석추정만, 실패해도 화면 동작)
                              ↓
[Railway API]           상시 가동 FastAPI — estimate / share
```

DB를 진실 원천으로 올리면 §2의 저장소 문제가 함께 풀린다. payload가 git에서 빠지고(`.git` 연 1.5GB 증가 해소), 읽기 성능은 그대로다. **§3 방안 B의 "외부 저장소"를 별도로 고를 필요가 없어진다.**

### 5.2 서비스 구성과 비용

Railway는 사용량 과금이므로 **상시 가동 서비스 개수가 곧 비용**이다.

| 서비스 | 가동 형태 | 비고 |
|---|---|---|
| Postgres | 상시 | 진실 원천 |
| API (FastAPI + lightgbm) | 상시 | 즉석 추정·공유를 넣을 때만 필요 |
| 배치 워커 | **cron/일시 기동** | 상시 가동 불필요 — 주간 갱신, 월 1회 재학습, 분기 horizon(11.8분) |

배치 워커를 상시로 두지 않는 것이 비용 측면에서 중요하다. 즉석 추정을 넣지 않기로 하면 API 서비스도 불필요하므로, **최소 구성은 Postgres 1개 + cron 워커**다.

### 5.3 원칙

- 배치 결과는 **스냅샷 단위로 통째 교체**한다(`as_of` 컬럼 + 트랜잭션 교체). 정적 payload와 DB가 어긋나지 않게 한다.
- 브라우저는 DB에 직접 접속하지 않는다. 읽기는 정적 JSON, 쓰기는 API 경유.
- DB 접속 정보는 Railway 환경변수와 Actions secret에만 둔다. `NEXT_PUBLIC_`에는 공개키만 붙인다.
- API가 죽어도 검색·담기·비교·지도는 계속 동작해야 한다. 프론트는 기능 플래그 뒤에서 연동하고 실패 시 정적 경로로 대체한다.

### 5.4 확인이 필요한 값

| 항목 | 왜 필요한가 |
|---|---|
| Railway 리전 | §1 지연 비교를 실제 값으로 채우기 위해. 권장은 바뀌지 않음 |
| 현재 플랜 티어와 이번 달 사용량 | §5.2 서비스 개수 결정 |
| 즉석 추정 기능 채택 여부 | API 서비스 필요 여부가 여기서 갈림 |

## 6. 권장 순서

| 순서 | 내용 | 선행 조건 | 예상 |
|---|---|---|---|
| 1 | horizon을 배치 전용으로 고정. 의존성을 가격 모델 서비스와 격리 | — | 0.5일 |
| 2 | 가격 학습을 월 1회 수동 트리거 배치로 분리 | — | 0.5일 |
| 3 | **Railway Postgres 구축 + 배치 산출물 스냅샷 적재** | §5.4 확인 | 1일 |
| 4 | payload를 DB에서 빌드해 정적 호스팅에 업로드, git에서 제거 | 3 | 0.5일 |
| 5 | `33`에 모델 아티팩트 저장 추가 + 동등성 검증(6,028행) | — | 1일 |
| 6 | 즉석 추정 채택 시 **방안 C** 상시 가동 API 구현 | 5 | 1~2일 |
| 7 | 공유 기능 — DB가 이미 있으므로 추가 비용이 작다 | 3 | 0.5일 |

가격 추론은 5단계까지 **현행 배치(A)를 유지**한다. 요구사항이 확정되기 전에 서빙 경로를 만들 이유가 없다.

## 7. 일정 관점

작성 시점은 D6(09-14)이고 제출은 D11(09-19~20)이다. [`project-charter.md`](project-charter.md) §6은 D8에 "Vercel + Supabase"를 두었으나, **제출 전에 읽기 경로를 API로 바꾸는 것은 순수 리스크다** — 얻는 것이 없고 심사 당일 죽을 경로만 하나 늘어난다.

- 제출 전: 1~2단계(배치 분리). 여유가 있으면 3~4단계(DB + 저장소 문제 해소)
- 제출 후: 5~7단계

## 8. 결정이 필요한 것

1. 즉석 추정 기능을 제품에 넣을지. 넣지 않으면 §4.3과 6단계가 전부 불필요하다
2. 공유 기능(`share`)을 넣을지 — 넣으면 개인정보 없는 익명 목록으로 한정
3. DB 승격 범위 — 진실 원천까지 올릴지(4단계 포함), 아니면 읽기 전용 사본으로 둘지
4. 제출 전 어디까지 진행할지 (§7)
