## 1. 추진 배경 및 필요성

아파트를 고를 때 일조와 조망은 실거주 만족도를 크게 좌우하지만, 현재 어떤 서비스도 이를 **탐색 조건**으로 쓰지 못한다.

호갱노노·직방·더스택은 이미 3D 단지투어로 계절별 일조량과 세대별 조망을 제공한다. 따라서 일조·조망 시뮬레이션 자체는 차별점이 아니라 **필수 기능**이다. 문제는 사용 방식에 있다 — 이들 서비스는 단지를 하나씩 열어 눈으로 **확인(inspection)** 하게 만든다. 서울 9,000개 단지를 그렇게 볼 수는 없다.

즉 시장에 없는 것은 시뮬레이션이 아니라 **시뮬레이션 결과로 전체를 정렬하는 탐색(search)** 이다.

## 2. 과제 목표

서울 전역 아파트를 대상으로 일조·조망·접근성을 사전 계산하고, 사용자가 조건을 걸면 **서울 전체가 즉시 정렬되는** 반응형 웹 서비스를 구축한다.

부차 목표로, 물리 시뮬레이션과 지도학습을 결합해 **런타임 생성형 AI 없이도 검증 가능한 AI 서비스**가 성립함을 보인다.

## 3. 과제 범위 (확정 제약)

| # | 항목 | 확정 내용 |
|---|---|---|
| 1 | 런타임 생성형 AI | **전면 금지.** 서비스 중 LLM 호출 0회 (개발 도구로서의 AI 에이전트는 자유) |
| 2 | 대상 | 서울 전역 아파트 단지 |
| 3 | 거래 유형 | 매매 + 전세 (월세 전용 단지 제외) |
| 4 | 폼팩터 | 반응형 웹앱, 모바일 우선 |
| 5 | 핵심 동선 | 지도 탐색 → 단지 클릭 → 리포트 |
| 6 | 타깃 | 실거주자 코어, 투자자는 확장 영역 |
| 7 | 비용 | 무료 API·무료 티어만 사용. 운영비 0원 |

**범위 밖**: 서울 외 지역, 오피스텔·빌라, 세대 단위(호수·향) 예측, 중개·거래 기능.

세대 단위 예측을 범위에서 제외한 이유는 공공 실거래 API가 층까지만 제공하고 향과 호수가 없어, 같은 동·같은 층에 남향과 북향이 공존하는 것을 구분할 수 없기 때문이다. 예측 단위는 **단지 × 면적타입 × 층대**로 확정했다.

## 4. 차별화 전략

**① 확인이 아니라 탐색**
조건을 걸면 서울 전체가 즉시 정렬된다. 발표 첫 30초를 필터링 데모로 구성해 이 차이를 시각적으로 드러낸다.

**② 환각 없는 검증 가능한 AI**
물리 시뮬레이션(horizon 엔진) + LightGBM + SHAP 조합. 모든 수치가 재현 가능하고 근거를 역추적할 수 있다. 생성형 AI의 환각 위험이 구조적으로 존재하지 않는다.

**③ 모르는 것을 모른다고 표기**
데이터가 없거나 신뢰도가 낮은 항목은 보간하지 않고 결측으로 남긴다. 매칭 실패 단지는 정렬에서 제외하고 회색 마커로 사유를 표기한다.

## 5. 시스템 구성

### 5.1 레이어 (단계별 완결 원칙)

각 레이어는 독립적으로 데모 가능해야 한다. 상위가 미완이어도 하위까지로 출품한다.

```
Layer 3  전세가율 · 정비사업 · 단지 비교              [여력 시]
   ▲
Layer 2  단지 시세 모델 (LightGBM)                   [목표선]
   ▲
Layer 1  ★ 지도 필터링·정렬 + horizon 지표  ← 차별점의 실체. 자원 집중
   ▲
Layer 0  데이터 수집 + 단지/건물 마스터
```

### 5.2 저장소 구조

```
data/     배치 파이프라인 — collect(수집) / master(마스터) / verify(검증) / archive(프로토타입)
models/   horizon 엔진 · 시세 모델
front/    Next.js 웹앱
docs/     문서 · mockups
output/   산출물 (커밋 제외)
```

분리 기준은 담당 역할이다 (§7). 스크립트 번호 접두사는 실행 순서이며 폴더를 가로질러 이어진다.

### 5.3 파이프라인

```
[배치 · Python · 로컬]
  공공데이터 수집 (실거래 API + OSM Overpass)
    → 단지/동 마스터 (지오코딩 + 공간 매칭)
    → horizon 엔진   ← 단일 연산에서 일조·개방도·향별값 전부 파생
    → 부가 지표 (도로근접, 표고, 생활 인프라)
    → 단지 시세 모델 → 적재

[런타임 · Next.js on Vercel]
  지도(카카오맵) → 필터·정렬 → 단지 클릭 → 리포트
  ※ 런타임 연산 없음. 전부 사전 계산 조회
```

**원칙: 런타임은 조회만 한다.** 데모 중 연산 지연·실패의 여지를 없앤다.

### 5.4 기술 스택

| 영역 | 선택 |
|---|---|
| 프론트 | Next.js 15 + TypeScript + Tailwind + shadcn/ui |
| 지도 | 카카오맵 JS SDK (무료 30만/일) |
| 배포 | Vercel 무료 티어 |
| DB | Supabase (Postgres + PostGIS) 무료 티어 |
| 배치 | Python 3.11, geopandas · shapely · pyproj · numpy |
| 태양 위치 | pvlib |
| ML | LightGBM + SHAP |

**좌표계 규칙**: 저장·표시는 WGS84(EPSG:4326), 거리·면적 연산은 EPSG:5179(UTM-K). 변환 누락은 반복 발생하는 버그이므로 유틸 하나로 강제하고 assert로 검증한다.

**D3 결과**: 한국부동산원 공동주택 단지 식별정보(서울 아파트 9,458건)를 지번주소로 조인해 정답 동수를 확보하고 배정 상한으로 걸었다. 동수 정확 일치율이 60.8%에서 **93.2%**로 올랐고 과다 배정은 1,760건에서 **0건**이 됐다. 준공년도를 등록 정보 기준으로 재측정하니 **99.9%** — 지오코딩과 단지 식별 자체는 사실상 완벽하며, D3의 문제는 처음부터 끝까지 동 배정 하나였다.

**남은 게이트 미달**: 동을 1개 이상 받은 단지가 72.7%로 기준 80%에 미달한다(거래량 가중으로는 96.8%). 원인은 알고리즘이 아니라 OSM에 해당 동이 없거나 `building=residential`로 태깅된 데이터 커버리지다.

**검증 주의**: 등록 동수를 배정 상한으로 쓰는 한, 등록 동수로 하는 검증은 과소만 잴 수 있고 "맞는 동을 골랐는가"는 재지 못한다. 그것은 층화 100건 수동 검수로만 확인된다 (§11).
