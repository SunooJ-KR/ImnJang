# 프론트엔드 협업 온보딩 — 임앤장

> 이 문서는 프론트엔드 작업자가 협업을 시작하기 전에 프로젝트의 목적, 기획 의도, 데이터 해석 방식, 화면 구현 원칙을 빠르게 숙지하기 위한 문서다.  
> 상세 근거는 `docs/product-identity.md`, `docs/data-contract.md`, `docs/data-model-and-ui.md`, `docs/implementation-plan.md`를 정본으로 삼는다.

---

## 1. 프로젝트 한 줄 설명

**임앤장(ImnJang)은 사용자가 관심 있는 서울 아파트 단지를 직접 담고, 같은 기준으로 나란히 비교하는 정적 웹 서비스다.**

서울 아파트 단지의 실거래가, 일조, 조망, 교통, 교육, 의료, 상권, 규제 정보를 미리 계산해 두고, 프론트엔드는 이 사전 계산 결과를 빠르게 검색·선택·비교하는 경험으로 풀어낸다.

중요한 점은 이 서비스가 “좋은 아파트를 골라주는 AI 추천 서비스”가 아니라는 것이다. 사용자가 이미 관심을 가진 후보들을 **같은 자로 재서 비교**하게 해 주는 도구다.

---

## 2. 왜 이런 제품인가

기존 부동산 탐색은 매물, 호가, 사진, 중개 설명 중심이다. 하지만 실제로 집을 보러 가기 전 사용자가 알고 싶은 질문은 더 구체적이다.

- 겨울에도 해가 얼마나 드는가?
- 앞이 얼마나 막혀 있는가?
- 역, 학교, 병원, 공원, 마트까지 얼마나 가까운가?
- 최근 실거래 기준으로 이 단지의 가격대는 어디쯤인가?
- 비슷한 조건의 다른 단지는 얼마에 거래됐는가?
- 데이터로는 알 수 없어서 현장에서 직접 봐야 할 것은 무엇인가?

임앤장은 이 질문에 대해 공공데이터와 물리 시뮬레이션으로 답한다. 다만 “살기 좋음”, “저평가”, “적정가”, “미래 상승 가능성”처럼 주관적이거나 투자 판단에 가까운 결론은 내리지 않는다.

프론트엔드는 이 선을 반드시 지켜야 한다. 화면이 단정적으로 보이면 제품의 신뢰성이 무너진다.

---

## 3. 제품 포지셔닝

### 한다

- 사용자가 고른 단지들을 같은 기준으로 비교한다.
- 최근 실거래가와 5년 추이를 보여준다.
- 실거래가 없을 때만 제한적으로 추정 구간을 보여준다.
- 일조·조망·생활 인프라를 가격과 분리해 환경 정보로 보여준다.
- 데이터가 없는 이유와 계산 한계를 화면 안에서 설명한다.
- 현장에서 확인해야 할 항목을 체크리스트로 남긴다.

### 하지 않는다

- 서울 아파트를 “좋은 순서”로 랭킹하지 않는다.
- 적정시세, 저평가, 고평가를 말하지 않는다.
- 일조·조망 때문에 가격이 얼마 오른다고 말하지 않는다.
- 현재 매물 가격이나 호가를 제공한다고 말하지 않는다.
- 임장을 대체한다고 말하지 않는다.
- 런타임 생성형 AI가 답변을 만들어 내는 것처럼 보이게 하지 않는다.

---

## 4. AI와 모델의 실제 역할

이 프로젝트에는 “AI/모델”이 있지만, 프론트에서 흔히 상상하는 챗봇형 AI 서비스가 아니다.

### 런타임 생성형 AI는 없다

서비스 화면에서 LLM을 호출하지 않는다. 사용자의 검색어를 AI가 해석하지 않고, 비교 리포트를 AI가 즉석 생성하지 않는다. 현재 프론트는 `front/public/data/` 아래 정적 JSON을 읽어 화면을 그리는 구조다.

이 결정은 의도적이다.

- 대회 제출물의 재현성과 속도를 높인다.
- 부동산·가격 문구에서 환각 위험을 제거한다.
- 서버 비용과 API 장애 가능성을 줄인다.
- 모든 문구를 사전 검증할 수 있게 한다.

### 모델은 “가격을 맞히는 만능 엔진”이 아니다

가격 기능은 **baseline-first** 원칙을 따른다.

1. 동일 단지 × 면적타입 × 층대의 최근 실거래가 있으면 그 값을 그대로 쓴다.
2. 동일 셀 거래가 없지만 같은 단지의 다른 거래가 있으면 단지 평균을 쓴다.
3. 단지 이력이 사실상 없을 때만 모델 추정값과 추정 구간을 쓴다.

즉 모델은 대부분의 가격 표시에 개입하지 않는다. 모델의 정당한 사용처는 “최근 2년 매매 거래가 없는 cold-start 단지”다.

### 일조·조망은 가격 모델에서 제외됐다

초기에는 일조·조망이 가격 예측에 도움을 줄 수 있다고 봤지만, 지역 통제 결함을 고쳐 재측정한 뒤 결론이 바뀌었다. 일조·조망은 통계적 연관은 일부 있어도 가격 예측 개선에는 거의 기여하지 않았다.

따라서 프론트에서는 다음 원칙을 지킨다.

- 일조·조망은 **환경 비교 정보**로 보여준다.
- 가격 블록과 일조·조망 블록을 문장으로 연결하지 않는다.
- “조망 때문에 비싸다”, “일조가 가격에 반영되지 않는다” 같은 단정은 금지한다.

## 5. 사용자가 보는 핵심 동선

```text
S1 검색 / 지도
  사용자가 단지명이나 동 이름으로 관심 단지를 찾는다.

S2 비교 담기
  2~4개 단지를 비교 대상으로 담는다.

S3 비교서
  가격, 유사 거래 사례, 환경 지표, 규제, 현장 확인 항목을 나란히 본다.
```

현재 구현은 이 동선을 정적 HTML/CSS/JS로 최소 구현한 상태다.

- `front/public/index.html`: 검색, 비교 영역, 하단 담기 바
- `front/public/app.js`: `index.json` 검색, `localStorage` 담기, 단지 JSON 비교서 렌더링
- `front/public/styles.css`: 모바일 우선 레이아웃
- `front/build/36.build_payload.py`: 정적 JSON payload 생성
- `front/build/37.check_wording.py`: 금지 문구와 필드명 검사

## 6. 프론트가 소비하는 데이터

프론트는 원천 데이터를 직접 다루지 않는다. 배치 스크립트가 만든 정적 payload만 소비한다.

### 검색 인덱스

`front/public/data/index.json`

```json
{
  "complexes": [
    {
      "id": "apt_seq",
      "n": "단지명",
      "g": "구",
      "u": "법정동",
      "lat": 37.5,
      "lng": 127.0,
      "y": 2015,
      "h": 1608
    }
  ]
}
```

검색용이라 키 이름을 짧게 줄였다. 초기 로딩 용량을 줄이는 것이 목적이다.

### 단지 상세

`front/public/data/complex/{aptSeq}.json`

프론트가 주로 쓰는 축은 다음과 같다.

- 기본 정보: `id`, `name`, `gu`, `umd_name`, `built_year`, `households`
- 매칭 신뢰도: `match_confidence`
- 환경: `env`
- 층대별 일조·조망: `floors`
- 가격: `price`
- 5년 추이: `series`
- 유사 거래 사례: `comparables`
- 규제: `regulation`
- 재건축: `redevelop`
- 현장 확인: `unknowns`

`null`은 “0”이 아니라 “정보 없음”이다. 프론트에서 임의로 0으로 채우면 안 된다.

## 7. 화면 문구의 절대 규칙

프론트 작업에서 가장 중요한 것은 UI보다 **표현의 정확성**이다. 부동산 가격·규제·환경 데이터는 문구 하나로 사실 왜곡이 될 수 있다.

### 가격 문구

`price[].source`에 따라 문구를 완전히 분기한다.

| source | 표시 의도 |
|---|---|
| `CELL_LAST` | 동일 단지·면적·층대의 최근 실거래 |
| `AREA_LAST` | 해당 층대 거래가 없어 같은 면적의 다른 층대 최근 실거래 사용 |
| `COMPLEX_MEAN` | 해당 면적 거래가 없어 단지 평균 사용 |
| `MODEL` | 최근 2년 매매 거래가 없어 모델 추정 사용 |
| `EXCLUDED` | 임대 관련 명칭으로 추정 대상에서 제외 |

특히 `MODEL`은 반드시 “추정”으로 표시하고, `est_low`~`est_high` 구간과 신뢰도 배지를 함께 보여줘야 한다.

### 금지 표현

- 적정시세
- 저평가 / 고평가
- 도보 N분
- 서울 전역 완전 검색
- 일조는 가격에 반영되지 않습니다
- 재건축으로 N% 오릅니다

도보 시간은 항상 “추정 도보 N분”이다. 역 거리는 역 중심이 아니라 **최근접 출입구 기준**이다.

### 규제 문구

토지거래허가구역은 기준일과 함께 표시한다.

예: `토지거래허가구역 (2026-08-16 기준)`

기준일 없는 “허가구역입니다”는 금지한다.

## 8. 프론트엔드 작업자가 해야 할 일

### 1순위: 비교 경험 완성

현재 검색 → 담기 → 비교서의 기본 골격은 있다. 다음 단계는 비교서가 실제 의사결정에 도움이 되도록 정보 위계를 다듬는 것이다.

- 가격, 유사 거래, 환경, 규제, 현장 확인을 명확한 블록으로 분리한다.
- 단지 2~4개를 모바일에서 세로로 비교해도 피로하지 않게 만든다.
- `MODEL` 가격은 실거래와 시각적으로 구분한다.
- 비교사례는 “실거래”와 “보정가격”이 다르다는 점을 작게라도 항상 붙인다.
- `match_confidence=FAILED` 단지는 실패 사유를 숨기지 않는다.

### 2순위: S1 검색과 필터 고도화

검색은 현재 단지명·동 이름 텍스트 검색 중심이다. 이후에는 지도와 필터가 붙어야 한다.

- 단지명/법정동 검색의 오타·부분 검색 UX를 개선한다.
- 조건 필터를 추가한다: 일조, 추정 도보, 가격대, 공원, 초등학교, 병원, 편의점 등.
- 조건 만족 개수를 즉시 갱신한다.
- 결과가 0개일 때 조건 완화 추천을 제공한다.
- Kakao Maps SDK는 배포 도메인 등록이 필요하므로, 지도 없이도 검색과 비교가 동작해야 한다.

### 3순위: 지도 UI

지도는 제품의 주장이 아니라 탐색 보조 수단이다.

- 정상 단지는 일반 마커로 표시한다.
- `match_confidence=FAILED` 단지는 회색 마커로 표시한다.
- 클릭 시 “건물 footprint 미매칭으로 일조·조망 분석 불가”처럼 이유를 보여준다.
- 지도 초기 로딩은 가볍게 유지한다.
- 줌아웃 상태에서 모든 상세 데이터를 한 번에 내려받지 않는다.

### 4순위: 근거와 한계 노출

임앤장의 신뢰성은 “모르는 것을 모른다고 말하는 것”에서 나온다.

- 모든 주요 숫자 옆에 계산 기준 또는 도움말 진입점을 둔다.
- 일조는 “동지 08~16시 총 N시간”으로 기준을 함께 보여준다.
- 도로·철도는 소음 dB가 아니라 “중심선까지 N m”로 보여준다.
- 승하차·혼잡도 결측은 “정보 없음”이 아니라 노선 운영주체 범위 차이를 설명한다.
- `unknowns`를 현장 확인 체크리스트로 노출한다.

### 5순위: 접근성과 모바일 품질

현재 방향은 모바일 우선이다.

- 400px 폭에서 가로 스크롤이 생기지 않게 유지한다.
- 검색 input은 iOS 확대 방지를 위해 16px 이상을 유지한다.
- 버튼은 엄지 조작이 가능한 크기로 둔다.
- 비교 카드가 길어질수록 접기/펼치기 또는 요약 우선 구조를 검토한다.
- 색상만으로 신뢰도나 상태를 전달하지 않는다.

## 9. 제안하는 UI 정보 구조

### 검색 화면

1. 검색창
2. 조건 필터 요약
3. 조건 만족 단지 수
4. 지도 또는 리스트
5. 하단 고정 비교 바

검색 화면의 목표는 “빠르게 후보를 담는 것”이다. 많은 설명은 비교서로 넘긴다.

### 비교서 화면

단지 카드마다 다음 순서를 권장한다.

1. 단지명, 구/동, 준공연도, 세대수
2. 규제/재건축 플래그
3. 가격
4. 5년 추이
5. 유사 거래 사례
6. 환경 지표
7. 데이터 한계와 현장 확인 항목

가격을 먼저 두는 이유는 사용자의 의사결정 기준점이기 때문이다. 다만 가격을 제품의 “판정”처럼 보이게 하면 안 된다.

## 11. 좋은 프론트 구현의 기준

- 빠르다: 정적 JSON 기반으로 검색과 비교가 즉시 반응한다.
- 정직하다: 추정, 결측, 기준일, 계산 가정을 숨기지 않는다.
- 비교하기 쉽다: 단지 간 차이가 같은 축으로 나란히 보인다.
- 과장하지 않는다: 가격·환경·AI를 마케팅 문장으로 엮지 않는다.
- 모바일에서 먼저 완성된다: 데모와 실제 사용 모두 휴대폰 화면을 기준으로 한다.
