# ImnJang 협업 가이드

이 저장소는 데이터 파이프라인, 모델, 프론트엔드, 문서를 분리해서 관리한다. 각자 맡은 영역에서 작업하되, 배포 대상 디렉터리에는 실행에 필요한 소스코드만 남기는 것을 원칙으로 한다.

## 핵심 원칙

- `main` 브랜치로 직접 push하지 않는다.
- 모든 작업은 별도 브랜치에서 진행하고, PR로 먼저 `dev`에 반영한다.
- `dev`에서 build 검증이 끝난 변경만 PR로 `main`에 병합한다. `main`은 배포된 상태와 같게 유지한다.
- 문서는 `docs/`에 모아 관리한다.
- `data/`, `models/`, `front/`처럼 프로젝트 실행이나 배포에 쓰이는 디렉터리에는 소스코드와 실행에 필요한 설정만 둔다.
- 작업 단위마다 commit하고, commit 메시지에는 무엇을 왜 바꿨는지 구체적으로 적는다.

## 디렉터리 기준

| 경로 | 용도 | 작성 기준 |
|---|---|---|
| `data/` | 데이터 수집, 가공, 검증 스크립트 | 파이프라인 실행 코드와 필요한 보조 코드만 둔다. |
| `models/` | 모델, 지표 계산, 예측 관련 코드 | 모델 실행에 필요한 코드와 최소 설정만 둔다. |
| `front/` | 프론트엔드 애플리케이션 | 화면, 컴포넌트, API 연동 등 배포 대상 소스만 둔다. |
| `docs/` | 기획서, 의사결정, 설계, 발표 자료, mockup 문서 | 설명 자료와 회의/결정 기록은 모두 이곳에 둔다. |
| `output/` | 실행 결과, 샘플 산출물 | 재현 가능한 결과 확인용으로만 사용하고, 큰 파일이나 민감한 파일은 commit하지 않는다. |

문서 성격의 파일이 `front/`, `models/`, `data/` 안에 필요해 보이면 먼저 `docs/`에 둘 수 있는지 검토한다. 단, 해당 디렉터리의 실행 방법을 설명하는 짧은 `README.md`는 예외로 허용한다.

## 브랜치 작업 흐름

브랜치는 세 층으로 쓴다.

| 브랜치 | 역할 |
|---|---|
| `main` | 배포 기준. 검증이 끝난 변경만 들어온다. 직접 push하지 않는다. |
| `dev` | 통합·검증 브랜치. 작업 브랜치가 여기로 먼저 모이고, 여기서 build를 검증한다. |
| 작업 브랜치 | 개별 작업. 최신 `dev`에서 분기한다. |

1. 작업 시작 전 최신 `dev`를 기준으로 새 브랜치를 만든다.
2. 브랜치 이름은 작업 영역과 목적이 드러나게 작성한다.
3. 작업 중에는 단위 변경마다 commit한다.
4. 작업이 끝나면 `dev`를 대상으로 PR을 열고 변경 내용, 확인 방법, 남은 이슈를 적는다.
5. `dev`에 merge한 뒤 `dev`에서 build를 검증한다.

   ```bash
   cd front && npx tsc --noEmit && npm run build
   ```

6. build와 필요한 확인이 통과하면 `dev` → `main` PR을 열어 병합한다. 실패하면 `main`으로 올리지 않고 `dev`에서 고친다.

`main`에 hotfix가 들어간 경우에는 `main`을 `dev`로 다시 merge해 두 브랜치를 맞춘다.

브랜치 이름 예시:

```text
feat/front-map-filter
fix/data-geocode-matching
docs/update-project-rules
model/horizon-metrics
```

## Commit 규칙

commit은 너무 크게 묶지 않는다. 한 commit은 하나의 의도가 분명해야 하며, 나중에 되돌리거나 검토하기 쉬워야 한다.

좋은 commit 메시지 예시:

```text
feat(front): add district filter to map search
fix(data): handle missing geocode result explicitly
docs: add collaboration workflow guide
model: calculate winter sunlight score per complex
```

피해야 할 메시지:

```text
update
fix
작업함
최종
```

commit 전에는 다음을 확인한다.

- 불필요한 임시 파일, 개인 설정, 대용량 산출물이 포함되지 않았는가
- 문서 파일이 `docs/` 밖에 흩어져 있지 않은가
- 실행 코드와 문서 변경이 한 commit에 과하게 섞이지 않았는가
- 변경 이유를 commit 메시지만 봐도 이해할 수 있는가

## PR 작성 기준

PR에는 최소한 다음 내용을 적는다.

- 변경 요약
- 테스트 또는 확인 방법
- 영향받는 영역: `data`, `models`, `front`, `docs` 등
- 리뷰어가 특별히 봐야 할 부분
- 아직 남은 작업이나 알려진 제한

PR은 작게 유지한다. 여러 영역을 동시에 건드려야 한다면 가능한 한 데이터, 모델, 프론트, 문서 변경을 구분해서 설명한다.

## 문서 관리

문서는 `docs/`에 목적별로 나눠 둔다.

- 의사결정은 `docs/decisions.md`에 근거와 함께 기록한다.
- 데이터 출처와 수집 기준은 `docs/data-sources.md`에 정리한다.
- 알고리즘과 모델링 판단은 `docs/algorithms.md` 또는 관련 문서에 남긴다.
- 발표, 기획, 로드맵, mockup 자료는 `docs/` 아래에 둔다.

코드 변경으로 사용법, 데이터 스키마, 실행 순서가 바뀌면 관련 문서도 같은 PR에서 갱신한다.

## 충돌 방지

- 같은 파일을 여러 명이 동시에 크게 수정해야 하면 먼저 작업 범위를 공유한다.
- 공통 인터페이스나 산출물 형식이 바뀌면 영향을 받는 담당자에게 먼저 알린다.
- `output/` 산출물을 기준으로 다음 단계가 동작한다면 파일명, 컬럼, 생성 조건을 PR에 명시한다.
- 급한 수정이라도 `main` 직접 push 대신 짧은 브랜치와 PR 흐름을 사용한다.

## 작업 전 체크리스트

- 최신 `dev`에서 브랜치를 만들었는가
- 내 작업이 어느 디렉터리에 들어가야 하는지 확인했는가
- 문서와 코드가 올바른 위치에 분리되어 있는가
- commit을 작업 단위로 나눌 계획이 있는가

## 작업 완료 체크리스트

- 단위 작업별 commit을 남겼는가
- commit 메시지가 구체적인가
- 실행 또는 검증 방법을 확인했는가
- 필요한 문서를 `docs/`에 갱신했는가
- PR 설명에 변경 요약과 확인 방법을 적었는가
- `dev`에서 build 검증(`npx tsc --noEmit && npm run build`)을 통과한 뒤 `main`에 올렸는가
