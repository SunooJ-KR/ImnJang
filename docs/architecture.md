# 아키텍처 — 임앤장

> 임앤장의 실행 구조를 한곳에 모은 문서다.  
> 제품 정의는 `docs/product-identity.md`, 프론트 데이터 계약은 `docs/data-contract.md`, 구현 순서는 `docs/implementation-plan.md`를 정본으로 삼는다.

---

## 1. 아키텍처 원칙

임앤장의 현재 MVP는 **배치 계산 → 정적 JSON 생성 → 정적 웹에서 조회**하는 구조다.

핵심 원칙은 다음과 같다.

- 런타임은 조회와 렌더링만 한다.
- 가격, 일조, 조망, 접근성, 비교사례는 사전에 계산한다.
- 브라우저는 정적 JSON을 받아 검색·담기·비교 화면을 구성한다.
- 서버 API, DB 조회, 런타임 LLM 호출은 현재 MVP 범위에 없다.
- 데이터 결측과 계산 한계는 숨기지 않고 화면에 드러낸다.

이 구조는 데모 중 연산 지연·서버 장애·생성형 AI 환각을 줄이고, 부동산 가격 문구를 사전에 검증하기 위한 선택이다.

## 2. 전체 구조

```text
[오프라인 배치 / 로컬 Python]
  공공데이터 수집
    ├─ 국토교통부 실거래 API
    ├─ OSM Overpass
    ├─ 건축물대장
    ├─ 서울교통공사 지표
    └─ 규제·정비사업 데이터

  데이터 가공
    ├─ 단지 마스터 생성
    ├─ 지오코딩
    ├─ 건물 폴리곤·동 배정
    ├─ 좌표계 변환
    └─ 품질 검증

  모델·지표 계산
    ├─ horizon 엔진: 일조·조망·개방도
    ├─ 접근성 지표: 역·학교·병원·상권·공원
    ├─ 가격 셀 집계
    ├─ cold-start 가격 추정
    └─ 유사 거래 사례 검색

  프론트 payload 생성
    ├─ front/public/data/index.json
    └─ front/public/data/complex/{aptSeq}.json

[런타임 / 정적 웹]
  사용자 브라우저
    ├─ index.json 로드
    ├─ 단지명·동명 검색
    ├─ 비교 대상 담기
    ├─ 단지 상세 JSON 로드
    └─ 비교서 렌더링
```

## 3. 레이어 구조

각 레이어는 독립적으로 데모 가능해야 한다. 상위 레이어가 늦어져도 하위 레이어만으로 제출할 수 있게 한다.

```text
Layer 3  전세가율 · 비교 기능 확장 · 지도 고도화          [여력 시]
   ▲
Layer 2  비교서: 가격 근거 + 환경 차이 + 현장 확인        [제품 목적지]
   ▲
Layer 1  검색·담기 + horizon 지표 + cold-start 모델
   ▲
Layer 0  데이터 수집 + 단지/건물 마스터 + 규제 정보
```

현재 제품의 중심은 Layer 2다. 지도와 필터는 “좋은 단지 순위”를 주장하는 기능이 아니라, 비교할 단지를 찾는 보조 수단이다.

## 4. 저장소 구조

```text
data/
  collect/     원천 데이터 수집
  master/      단지·동 마스터 구축
  verify/      데이터 정합성 검증
  archive/     폐기되거나 보존용인 프로토타입

models/
  horizon/     일조·조망·접근성·교통 지표 계산
  price/       가격 셀, cold-start 추정, 비교사례 생성

front/
  build/       프론트용 정적 payload 생성·문구 검사
  public/      배포 대상 정적 웹앱

docs/
  제품 정의, 데이터 계약, 구현 계획, 화면 설계, 아키텍처

output/
  배치 산출물. 대용량 파일이며 기본적으로 커밋하지 않는다.
```

스크립트 번호 접두사는 실행 순서에 가깝다. 폴더를 가로질러 이어질 수 있으므로 숫자만 보고 같은 디렉터리 안에서만 흐름을 판단하면 안 된다.

## 5. 데이터 파이프라인

### 5.1 수집

수집 레이어는 외부 원천을 로컬 파일로 확보한다.

- 실거래 매매·전월세: 가격 화면, 가격 추이, cold-start 추정의 원천
- OSM: 건물, 도로, 철도, 공원, 학교, 병원, 상점, 수계, 산
- 건축물대장: 세대수, 동 수, 용적률, 건폐율, 주차
- 서울교통공사: 승하차, 혼잡도
- 규제·정비사업: 토지거래허가구역, 재건축 추진 정보

외부 API 호출은 배치 시점에만 일어난다. 런타임 프론트는 원천 API를 직접 호출하지 않는다.

### 5.2 마스터 구축

수집 데이터는 `apt_seq`를 중심으로 단지 마스터에 연결된다.

- `apt_seq`: 실거래 API의 단지 키이며 프론트 상세 JSON 파일명으로도 쓰인다.
- 지오코딩: 단지 위치를 확보한다.
- 동 배정: 단지와 건물 폴리곤을 공간 매칭한다.
- `match_confidence`: 동 배정 신뢰도를 `HIGH` / `MEDIUM` / `LOW` / `FAILED`로 기록한다.

`FAILED` 단지는 숨기지 않는다. 지도와 비교서에서 “건물 footprint 미매칭으로 일조·조망 분석 불가”처럼 이유를 표시한다.

### 5.3 지표 계산

`models/horizon/`은 단지 환경 비교에 필요한 물리·접근성 지표를 만든다.

- 일조: 동지 기준 시간
- 조망: 개방도, 한강·공원·산 조망 여부
- 교통: 지하철 출입구 직선거리, 추정 도보 시간, 승하차·혼잡도
- 교육: 초등학교 거리, 초품아 근사
- 의료: 종합병원·상급종합병원 거리, 의원·소아 표방 기관 수
- 생활: 마트, 백화점, 슈퍼, 편의점, 음식점, 공원
- 소음 대체: dB 추정이 아니라 도로·철도 중심선 거리

일조·조망은 가격 모델 설명에 쓰지 않고, 환경 비교 화면 전용으로 쓴다.

### 5.4 가격 계산

가격은 baseline-first 구조다.

```text
동일 단지 × 면적타입 × 층대 최근 거래 있음
  → 최근 실거래 표시

동일 셀 거래는 없지만 같은 단지 거래 있음
  → 단지 평균 표시

단지 이력이 사실상 없음
  → cold-start 모델 추정 + 구간 + 신뢰도 표시
```

프론트의 `price[].source`는 이 분기 결과다.

- `CELL_LAST`: 최근 실거래
- `COMPLEX_MEAN`: 단지 평균
- `MODEL`: 모델 추정
- `EXCLUDED`: 매매 거래 표시 제외

`MODEL`은 반드시 “추정”으로 보인다. 실거래와 같은 톤으로 섞으면 안 된다.

### 5.5 비교사례 생성

비교사례는 “비슷한 조건의 다른 단지는 보통 얼마에 거래됐는가”를 보여주기 위한 근거다.

선정 순서는 고정한다.

1. 면적타입 유사
2. 준공년도 유사
3. 세대수 규모 유사
4. 반경 3km 이내
5. 환경 feature 유사도

적합한 사례가 부족하면 개수를 채우지 않는다. 보정가격은 실제 체결 가격이 아니므로 프론트에서 반드시 별도 설명을 붙인다.

## 6. 프론트 런타임 구조

현재 프론트는 `front/public/` 아래 단일 정적 앱이다.

```text
front/public/
  index.html       화면 구조
  app.js           검색·담기·비교 렌더링
  styles.css       모바일 우선 스타일
  data/
    index.json
    complex/
      {aptSeq}.json
```

런타임에서 하는 일은 제한적이다.

- `index.json`을 한 번 로드한다.
- 단지명·법정동 문자열 검색을 브라우저에서 수행한다.
- 비교 대상은 최대 4곳까지 `localStorage`에 저장한다.
- 비교 버튼을 누르면 각 단지 상세 JSON을 fetch한다.
- JSON 값에 따라 가격, 유사 거래, 환경, 규제, 현장 확인 항목을 렌더링한다.

런타임에서 하지 않는 일은 다음과 같다.

- 실거래 API 호출
- DB 쿼리
- 가격 모델 추론
- 일조·조망 계산
- 유사 단지 검색 알고리즘 실행
- LLM 호출

## 7. 정적 payload 계약

### 7.1 검색 인덱스

`front/public/data/index.json`

```json
{
  "complexes": [
    {
      "id": "11680-1",
      "n": "래미안대치팰리스",
      "g": "강남구",
      "u": "대치동",
      "lat": 37.5,
      "lng": 127.05,
      "y": 2015,
      "h": 1608
    }
  ]
}
```

검색 인덱스는 초기 로딩을 위해 키를 짧게 유지한다.

### 7.2 단지 상세

`front/public/data/complex/{aptSeq}.json`

```json
{
  "id": "11680-1",
  "name": "래미안대치팰리스",
  "gu": "강남구",
  "umd_name": "대치동",
  "built_year": 2015,
  "households": 1608,
  "match_confidence": "HIGH",
  "env": {},
  "floors": [],
  "price": [],
  "series": [],
  "comparables": [],
  "regulation": {},
  "redevelop": {},
  "unknowns": []
}
```

`null`은 정보 없음이다. 프론트에서 0으로 대체하지 않는다.

## 8. 배포 구조

현재 배포 대상은 `front/public/`의 정적 파일이다.

```text
Vercel
  └─ front/public
       ├─ index.html
       ├─ app.js
       ├─ styles.css
       └─ data/
```

지도는 Kakao Maps JS SDK를 붙이는 방향이지만, 지도는 도메인 등록이 필요하다. 따라서 지도 SDK가 없어도 검색·담기·비교는 동작해야 한다.

향후 서버가 필요해지는 경우는 다음과 같다.

- 실시간 매물 또는 호가 연동
- 사용자 계정과 저장 목록 동기화
- 동적 지도 bbox API
- 데이터 갱신 자동화
- 대용량 검색 인덱스 분할 제공

현재 MVP에서는 위 항목을 의도적으로 제외한다.

## 9. 검증과 품질 게이트

### 9.1 데이터 검증

배치 스크립트는 산출물 생성과 함께 자체 검증을 수행해야 한다.

- 키 유일성
- 행 수와 커버리지
- 좌표계 변환 정합성
- 가격 범위
- 결측 처리
- `match_confidence` 분포
- payload 크기

### 9.2 프론트 문구 검증

프론트 문구는 `front/build/37.check_wording.py`로 검사한다.

```bash
.venv/bin/python front/build/37.check_wording.py
```

검사 대상은 다음과 같다.

- 금지 표현 사용 여부
- `app.js`에서 참조하는 JSON 필드명
- `price[].source` 4종 분기 완전성

금지 표현은 기능 문제가 아니라 사실 왜곡으로 본다.

## 10. 주요 아키텍처 결정

| 결정 | 이유 |
|---|---|
| 런타임 서버 없음 | 데모 안정성, 비용 절감, 재현성 확보 |
| 정적 JSON을 API처럼 사용 | 모든 계산을 사전에 끝내고 브라우저는 조회만 수행 |
| 런타임 LLM 호출 없음 | 부동산 가격 문구 환각 방지, 사전 검증 가능 |
| `apt_seq` 중심 키 사용 | 실거래 API 상세 엔드포인트의 안정 키 |
| 일조·조망을 가격 모델에서 제외 | 재측정 결과 가격 예측 개선이 0과 구별되지 않음 |
| `match_confidence=FAILED` 노출 | 모르는 것을 숨기지 않는 제품 원칙 |
| 소음 dB 모델 폐기 | 캘리브레이션 라벨이 없어 거리 지표로 대체 |
| 지도는 보조 수단 | 제품 약속은 랭킹이 아니라 비교서 |

## 11. 프론트 작업자가 기억할 점

- 프론트는 계산 엔진이 아니라 검증된 결과를 보여주는 표현 계층이다.
- 가격 문구는 `price[].source`만 보고 분기한다.
- “추정”, “정보 없음”, “기준일”, “현장 확인”을 숨기지 않는다.
- 지도 없이도 핵심 동선이 동작해야 한다.
- 데이터가 비어 있을 때도 실패처럼 보이지 않게, 이유를 설명해야 한다.
- 새 문구를 추가하면 반드시 문구 검사를 통과시킨다.
